Pi Agent 入门到进阶

Pi 是什么？

Pi 是住在你终端（命令行窗口）里的 AI 助手：你给它一个目标和一个文件夹，它会自己看文件、跑命令、改内容，一步步把事情做完。

平时用聊天机器人，你问它、它答你，最后还得你自己去复制粘贴、动手改文件。Pi 不一样：它不只会"说"，还会"做"。

想象你身边坐了一位勤快的实习生。你说"把会议纪要整理成待办清单存到 action-items.md"，他会自己打开文件、阅读、整理、保存，再向你汇报——而不是递给你一段文字让你自己去弄。

一句话官方定位

Pi 官方把自己描述为 minimal, extensible agent harness（极简、可扩展的 agent 外壳）。拆开看：

点击卡片翻面，认识 4 个关键词
Agent（智能体）
能自己决定"下一步做什么"并动手执行，直到完成目标的 AI 程序。
模型（Model）
真正"思考"的大脑，如各家的大语言模型。Pi 自己不是模型，它需要接入一个。
Harness（外壳）
包在模型外面的那一层：负责给模型"手脚"（读写文件、跑命令）、管理对话记录、显示界面。
终端（Terminal）
黑底白字的命令行窗口。Pi 在这里运行，在你指定的文件夹里工作。
Pi = 模型（大脑）+ Pi 这层外壳（手脚与记忆）。极简的意思是：自带功能刻意很少，其余靠你按需扩展。
"极简"到什么程度？先想一想，再点开 官方说明 Pi 自带强力的默认功能，但刻意不内置子代理（sub-agents）和计划模式（plan mode）。想要这些，你可以让 Pi 帮你做出来，或者安装别人做好的扩展包。这就是"可扩展"的含义：让 Pi 适应你的工作方式，而不是你去适应它。

说明：本课程讲的是 pi.dev 的 Pi（npm 包 @earendil-works/pi-coding-agent），内容依据其官方文档整理；具体版本的细节请以 pi --help 和官方文档为准。

Pi 是"会动手的 AI 助手"，由模型提供智力、由 Pi 外壳提供手脚；它极简，靠扩展成长。

核心概念：模型、工具、会话、上下文

理解 4 个词，就理解了 Pi 的全部骨架：模型负责想，工具负责做，会话负责记，上下文是模型这一刻能"看到"的内容。

概念含义类比
模型 / 提供商模型生成回复；提供商是你获取这个模型的服务或账号（订阅、API key、本地模型都可以）大脑 / 租大脑的公司
工具（tool）模型可以调用的"动作"，如读文件、执行命令手脚
会话（session）一次对话的完整记录：消息、工具调用与结果、换模型、压缩等事件，自动保存工作日志
上下文（context）发给模型的内容：系统提示 + 当前分支的对话历史 + 工具定义 + 技能描述摆在大脑面前的资料

Pi 的内置工具

默认启用 4 个工具：read、bash、edit、write；另有 grep、find、ls 可按需选择。点一点看看各自做什么：

工具探索器

read（默认启用）：读取文本文件和支持的图片。

例：先读 README.md 才知道该改哪里。

bash（默认启用）：在你的电脑上执行命令行命令。

例：运行测试、查看 git 状态、安装依赖。它拥有 Pi 进程的系统权限——所以最强大，也最需要小心。

edit（默认启用）：对已有文件做局部修改。

例：把文件里的某段文字替换掉。

write（默认启用）：写入文件（比如新建一个文件）。

例：把整理好的待办存成 action-items.md。

grep（可选）：搜索文件内容。

例：找出哪些文件提到了 "TODO"。

find（可选）：按 glob 模式查找路径。

例：找出所有 *.test.js。

ls（可选）：列出目录内容。

例：看看项目根目录有什么。

用 --tools 选择工具。写普通名字会替换整个默认选择；用 +名字 / -名字 则是在默认基础上增减，例如 pi --tools +codemode,-write。两种写法不能混用。

例如只读审查（不给它改文件的工具）：

pi --tools read,grep,find,ls --print "Review this project"

你想让 Pi 审查项目代码，但不希望它有任何写入能力。最合适的启动方式是？

模型想、工具做、会话记、上下文是模型此刻看到的资料。工具默认 read/bash/edit/write，用 --tools 调整。

Agent 循环：一次任务如何被完成

Pi 反复做一件事：把对话发给模型 → 模型回复（可能带工具调用）→ Pi 执行工具并记录结果 → 若还需继续就再来一轮，否则结束。

像"点单—厨房—上菜"的循环：你点单（消息）→ 厨师看完菜谱（模型）说"我需要先看看冰箱"（工具调用）→ 服务员（Pi）去看冰箱并报告（工具结果）→ 厨师再决定下一步……直到厨师说"菜好了"（没有更多工具调用）。

每一轮（turn）里发生了什么

  1. Pi 用系统提示 + 当前分支历史 + 可用工具 + 模型设置组装请求，发给所选提供商。
  2. 提供商以流式返回助手回复，里面可能有文字，也可能有工具调用。
  3. Pi 记录回复，逐个执行工具调用并记录结果——这就是一轮。
  4. 如果工具结果或排队消息需要再请求一次模型，就开始下一轮；否则这次运行结束。

注意两点：① 每个工具结果都会让上下文变长；② 只有当模型的回复不再包含工具调用（且没有排队消息）时，运行才结束。勾选"中途插话"再试一次：你的 Enter 消息不会打断正在执行的那一步，而是在这批工具调用结束后影响下一次模型回复。

Pi 的一次运行（run）在什么情况下结束？

一轮 = 请求模型 + 执行其工具调用。有工具结果要继续就再来一轮，没有就结束。

上下文与压缩（compaction）

模型一次只能"看"有限长度的内容（上下文窗口）。对话越长越快塞满；Pi 通过压缩：把较早的历史换成一段摘要，保留最近的消息。

每次请求，Pi 会发送：系统提示、已发现的上下文文件（如 AGENTS.md）、工具定义、技能描述，以及当前分支的对话历史。底部状态栏会显示上下文用量。接近模型上限时，Pi 通常会自动压缩；你也可以随时用 /compact 手动压缩，还能附加说明，比如"请务必保留关于数据库的决定"。

"压缩"不是"删除"。压缩会插入一条摘要，在之后的请求里替代旧消息，但原始记录仍保留在会话文件中。
上下文窗口示意（单位为抽象的"块"，非真实 token 比例）

灰块 = 系统提示/工具定义等固定开销；蓝块 = 对话轮次；紫块 = 压缩摘要（示意其大小约为被压缩内容的 1/5，真实比例取决于内容）；红块 = 超出窗口的部分。

思考：为什么要保留"最近的"几轮而不是全部摘要？最近的消息通常与当前正在做的事最相关，且细节（刚读的文件内容、刚出现的报错）最不能丢；较早的往往只需要保留"结论与决定"。

执行 /compact 之后，关于原来的旧消息，哪个说法正确？

上下文有上限；压缩 = 摘要替换旧历史、保留最近消息，原始记录不丢。

会话树：随时回头、分叉探索

Pi 的会话不是一条直线，而是一棵树。回到过去某一步换个说法，不会抹掉你离开的那条分支。

会话保存为 JSONL 文件，每个条目有自己的 ID 并指向父条目。从根到"当前条目"的这条路径叫活动分支——只有它会被发给模型。从较早的条目继续，就会在同一个文件里长出新分支。

点击任意节点，把它设为"当前位置"（蓝框消息 = 你；白框 = Pi）

下面三条命令都用来"走另一条路"，区别在于放在哪：

命令结果适用
/tree在当前会话文件内跳转几种方案想放在一起比较
/fork从较早的用户消息创建新会话另一种方案应成为独立工作
/clone把活动分支复制成新会话想要当前状态的独立副本

离开某个分支时，Pi 还可以为它生成摘要并附到你进入的分支上，这样被放弃路线里有价值的发现不会白白丢掉。

定制 Pi：从最轻的机制开始

Pi 提供一整套由轻到重的定制机制。官方建议：用能满足需求的最不强大的那一个。

我想要……（点选需求，看该用哪个机制）

→ AGENTS.md（上下文文件）

Pi 会从用户目录（默认 ~/.pi/agent）、工作目录及其父目录加载 AGENTS.md（也认 CLAUDE.md）。放在哪个目录，就在该目录及其以下生效。同目录下可用 AGENTS.override.md 覆盖。

→ 提示模板（Prompt template）

放在 ~/.pi/agent/prompts/ 或项目的 .pi/prompts/，会出现在 / 命令菜单里，输入前展开为可复用的消息文本。

→ 技能（Skill）

一个含 SKILL.md 的文件夹，可附带脚本、参考资料。比提示模板重，但不需要新增可执行的集成点。放在 skills/ 目录或 .agents/skills/，可用 /skill:名称 强制调用。

→ 扩展（Extension）

TypeScript 模块，运行在 Pi 进程内，可注册工具、命令、快捷键、事件处理器、模型提供商、渲染器等。能力最强，也拥有与 Pi 相同的系统权限，只装可信来源。

→ 终端 UI（TUI）扩展组件

需要自定义终端界面组件时使用（官方文档有专门的 Terminal UI 章节）。

→ 自定义提供商（Custom provider）

连接内置没有的模型服务；扩展里也可用 pi.registerProvider() 注册。兼容端点还可在 models.json 中配置。

→ Pi 包（Pi package）

把扩展、技能、提示模板、主题打包，通过 npm 或 git 安装、分享。

三个最小示例

① AGENTS.md（项目根目录，内容由你定）

# 项目约定
- 提交前运行 npm test
- 不要修改 dist/ 目录

② 技能：pdf-tools/SKILL.md

---
name: pdf-tools
description: Extract text and tables from PDF files. Use when reading, converting, or inspecting PDFs.
---

# PDF tools
Read references/formats.md before converting a document.

description 决定模型何时考虑加载这个技能，要写清"做什么、何时用"。Pi 启动时只把每个技能的名称、描述、路径放进系统提示，需要时才读取完整的 SKILL.md，这样详细指导不会白白占用上下文。

③ 扩展：~/.pi/agent/extensions/hello.ts（官方文档示例）

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerCommand("hello", {
    description: "Show a greeting",
    handler: async (name, ctx) => {
      ctx.ui.notify(`Hello, ${name || "world"}!`, "info");
    },
  });
}

启动 Pi 后运行 /hello。开发时可用 pi --extension ./hello.ts 直接加载（Pi 使用 jiti，无需单独编译 TypeScript）。修改后用 /reload 重新加载。

Pi 启动时，对一个已安装的技能（skill），系统提示里放的是？

AGENTS.md → 提示模板 → 技能 → 扩展 → 包：能力与风险依次递增，从最轻的开始。

自动化与嵌入：不只是聊天界面

同一个 Pi 内核有 4 种"外壳"：交互界面、print 模式、JSON 事件流、RPC，以及 TypeScript SDK。它们共用同样的 agent 与会话机制。

我的场景是……

交互模式：直接运行 pi。

print 模式：运行提示，把最终回复写到 stdout 后退出。

pi --print "Summarize this repository"
git diff | pi --print "Review this change"

当 stdin 或 stdout 被重定向且未选择 JSON/RPC 时，Pi 也会使用 print 模式。

JSON 模式：把 JSONL 事件写到 stdout 后退出。

pi --mode json "Inspect this repository" > events.jsonl

RPC 模式：pi --mode rpc 从 stdin 读取 JSONL 命令，把响应和事件写到 stdout，直到关闭。适合由另一个进程控制 Pi。注意 RPC 模式不接受 @file 参数。

TypeScript SDK：在你的应用进程内创建并控制 agent 会话，无需起子进程。

--print 控制"是否运行一次就退出"；--mode 控制"输出接口"。--mode text 在终端里仍会打开界面，要一次性运行请用 --print。JSON/RPC 模式独占 stdout 传递协议记录。

常用的会话控制参数：--continue（-c）续接最近会话、--resume 打开选择器、--no-session 不保存（临时运行，退出后无法恢复）。

你想从另一个独立的程序里，通过标准输入输出持续控制 Pi 的运行。应选？

交互 / print / JSON / RPC / SDK：同一内核的五种用法，从"手动用"到"被程序驱动"。

安全边界与设计取舍

Pi 的工具和扩展以Pi 进程的系统权限运行，没有内置沙箱。便利与风险同源：你要自己决定它在哪里、能碰什么。

机制它做什么它不做什么
项目信任（project trust）决定是否加载项目里的设置与资源（.pi/ 等）不是沙箱，不限制工具调用
--tools 选择工具减少模型可调用的工具不会限制剩下的工具（如 bash）的系统权限
容器 / 沙箱从系统层面限制可触达范围需要你自己搭建（文档建议用于不可信或无人值守场景）

设计取舍：为什么 Pi 要"极简"

Pi 选择少内置、多扩展：把子代理、计划模式这类功能留给你按需定制。好处是内核小而透明、可按工作流塑形；代价是你需要自己承担更多选择——包括安全边界。哪种取舍更好因人而异，建议先从默认配置用起，遇到真实痛点再扩展。
