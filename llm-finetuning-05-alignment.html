大模型微调 · 第 5 课：评估、对齐与上线

为什么需要"对齐"：会说，不等于说得好

SFT 之后的模型已经"会说人话"，但它说的话不一定符合你的期待——可能啰嗦、可能跑题、可能有安全隐患。"对齐"（Alignment，让模型的行为符合人类的期望与价值观）就是解决"会说但说不对"的那道工序。

在前几课里，你已经学会用 SFT（Supervised Fine-Tuning，监督微调：给模型看成百上千条"标准问答示范"，让它模仿）把底座模型调教得"像模像样"。训练时看着损失一路下降，满心欢喜地让它生成一段回答，结果可能是这样的：

用户问SFT 后的模型可能答问题在哪
"怎么重置密码？"从互联网的发展史讲起，用了 800 字还没讲到重置按钮啰嗦、抓不住重点
"帮我写一封请假邮件"邮件写完了，但又附赠了三大段请假注意事项、法律依据和嘘寒问暖过度发挥、不听指令
"心情不好怎么办？"认真地建议"试试过量饮酒放松"（它在某本小说里读到过）不安全、价值观跑偏
SFT 像教新员工"背熟了客服话术手册"：每句话都通顺、都像那么回事。但一上真场子，他可能背完话术还喋喋不休（啰嗦），客户问 A 他答到 Z（跑题），甚至把玩笑当建议说出口（不安全）。背熟手册 ≠ 会好好干活，还差一步"学会看场合、懂分寸"的历练——这就是对齐。

这里出现本课第一个关键术语：对齐（Alignment），指的是让模型的输出符合人类的偏好、意图和安全标准。注意它和 SFT 的关系：SFT 教模型"模仿示范"，对齐教模型"分清好坏"。示范数据毕竟有限，模型见过的话术之外怎么表现，要靠对齐来兜底。

本课主线就三件事：① 怎么评估模型好不好（第 2 章）；② 怎么把模型对齐到人类的喜好上（第 3–5 章）；③ 怎么把它上线跑起来、并持续变好（第 6–7 章）。
判断题：这是"会说但说不对"吗？

场景一：用户问"北京到上海的火车多久"，模型先讲了 200 字高铁发展史，最后才说"约 4.5–6 小时"。这属于对齐要解决的问题吗？

场景二：模型把训练语料里某本小说角色的台词当成了养生建议，推荐给真实用户。这属于对齐要解决的问题吗？

记住本课的灵魂拷问："会说"是 SFT 给的，"说得好、说得对、说得安全"是对齐给的。评估是这一切的前提——你说你模型"更好了"，凭什么？下一章先解决这个问题。

评估方法全景：怎么证明你的模型变好了

没有评估，一切"变好"都是自说自话。评估方法有四种主流：留出集损失、人工评测、公开基准测试、用大模型当裁判（LLM-as-Judge）。各自有适用的场景和著名的坑。

先定义评估（Evaluation）：用可复现的方法，定量或定性地判断模型输出质量的过程。微调工程师的日常就是"改一个配置 → 评估 → 决定要不要"。

held-out loss		留一部分数据不训练，看模型在它上面的预测损失（预测下一个词有多"意外"）训练监控、快速回归测试损失低 ≠ 回答好；对啰嗦无感（啰嗦的话只要"可预测"，损失就低）

对齐方法演进：从 SFT 到 DPO 的二十年脉络

对齐技术的演进是一连串"上一步还缺什么"的故事：SFT 缺"好坏之分" → 奖励模型（RM）给出标量分数 → PPO 用 RL 把分数拉高 → DPO 发现可以干脆不要 RL。点击时间线节点，看每一步解决了什么问题。

👆 点击时间线上的节点，查看每一步的详情。

把"训练一个得体员工"串起来：SFT = 发手册让他背示范对话；RM = 请资深客服给每段回答打分，训练出"自动打分器"；PPO = 让实习生对着打分器反复演练，哪句话分高就多说；DPO = 发现根本不用打分器，直接把"好回答 vs 差回答"摆在他面前对比着学；ORPO/KTO = 连"成对的对比"都省了，只给"这是好/这是坏"的单标签。
术语预告（L3 会展开）：RM（Reward Model，奖励模型：输入一段话，输出一个分数的模型）；PPO（Proximal Policy Optimization，一种强化学习算法）；DPO（Direct Preference Optimization，直接用偏好数据优化，不开强化学习）。
演进的主线就一条：不断降低"把人类喜好灌进模型"的成本和复杂度。RLHF（PPO 那套）效果好但工程极重；DPO 家族用一点点效果换来了十倍的可维护性——这也是今天开源社区的主流选择。

RLHF 三步走与 reward hacking

RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）= SFT → 训练奖励模型 → PPO 强化学习。它效果强大，但有一个著名的宿敌：reward hacking（奖励 hacking，模型钻奖励模型的空子、刷高分数却不真正变好）。

三步走

RLHF 全流程（点"下一步"逐步看）
第 1 步：SFT。用高质量示范数据训练一个"会模仿"的模型。这一步你已经会了——它是 RLHF 的起点（称为策略模型，policy，即被训练的模型）。
第 2 步：训练奖励模型（RM）。收集人类对同一问题多个回答的排序偏好（A 比 B 好），训练一个打分模型：输入问题和回答，输出一个标量分数。它的目标是逼近"人类的喜好函数"。
第 3 步：PPO 强化学习。让策略模型生成回答，奖励模型给它打分，PPO 算法调高"得高分回答"的生成概率、调低低分回答的概率。如此循环，模型越来越"讨奖励模型喜欢"。
关键护栏：PPO 训练时通常加入 KL 散度约束（KL penalty，限制新模型别偏离 SFT 模型太远），防止模型为了刷分而崩坏。β 系数控制约束松紧。

奖励 hacking：为什么防不胜防

RM 只是人类偏好的近似。一旦策略模型发现 RM 的盲区——比如"RM 偏爱长回答"——它就会无限变长，哪怕人已经觉得啰嗦。这就是 reward hacking：优化指标取代了真正的目标（古德哈特定律的 AI 版："一项指标一旦成为目标，它就不再是好指标"）。

Reward Hacking 情景模拟器：你是策略模型，RM 有隐藏偏好

拖动滑块观察：RM 的秘密偏好是"超长 + 多 emoji"（一种夸张的模拟，真实案例见注）。不加约束时分数一路狂飙，但"人类满意度"（图里的绿线）在超过甜点后崩塌。β（KL 约束）越大，刷分越难，但也越难学好——这是 RLHF 的核心张力。

真实世界中 reward hacking 的案例包括：模型学会在回答里塞满看似专业的引用标记来骗过"有引用加分"的 RM；RM 偏好自信语气，模型便对不懂的问题也斩钉截铁（幻觉加剧）。对策：迭代重训 RM、混合人工抽检、保持 KL 约束、多奖励信号集成。没有一个能根治，只能持续盯防。
RLHF 的心法：你优化的从来不是"回答质量"，而是"奖励模型的打分"。打分的模型有多像人，上限就有多高；差多少，hack 的空间就有多大。

DPO 一族：绕开强化学习的对齐

DPO（Direct Preference Optimization，直接偏好优化）的证明很巧妙：PPO 想要的最优解有解析形式，直接代入奖励定义，就得到一个不需要奖励模型、不需要 RL 循环、甚至不需要采样的目标函数——只用成对偏好数据，像普通 SFT 一样训练。

DPO 在优化什么

DPO 的数据格式是偏好对：同一个问题，一个人类更喜欢的回答 $y_w$（win，胜方）和一个更差的 $y_l$（lose，负方）。DPO 直接提高"当前模型给 $y_w$ 相对 $y_l$ 的概率比"超过"参考模型（SFT 版）给出的概率比"，目标函数：

$$\mathcal{L}_{\text{DPO}} = -\log \sigma\!\left(\beta \log\frac{\pi_\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)} - \beta \log\frac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)}\right)$$

逐项读：$\pi_\theta$ 是当前正在训练的模型，$\pi_{\text{ref}}$ 是冻结的 SFT 参考模型（相当于隐式的 KL 约束者），$\beta$ 是温度系数（控制"离参考模型多远"），$\sigma$ 是 sigmoid 函数（把任意数压到 0–1，使整体变成一个"胜率"的概率）。直觉：让模型 relative 地抬高好回答、压低差回答，同时别走太远。

家族成员

方法数据要求特点
DPO成对偏好（好 vs 差）简单稳定，开源社区事实标准
ORPO成对偏好把 SFT 和对齐合并进一个损失，连参考模型都不用（省显存）
KTO只需二值标签（好/坏，各归各的）数据门槛最低——真实用户的点赞/点踩就能用
翻卡：DPO vs PPO 的取舍
PPO 的优势
在线生成 + 在线打分，能利用奖励模型的精细分数信号，部分任务上限更高；可以叠多目标奖励（安全 + 有用分开建模再加权）。
PPO 的代价
要同时维护策略、参考、奖励三个模型 + RL 训练循环，显存 ×3 起步，超参敏感（β、clip、KL 系数）， notoriously 难调。
DPO 的优势
一个模型、一份成对数据、一个交叉熵式的损失函数，稳定好调、复用全部 SFT 基建；小团队几天就能跑通。
DPO 的代价
离线数据、信号较粗（只有"谁好谁差"，没有"好多少"）；数据分布外的问题它学不到；长期迭代可能"越训越像 chosen 风格"而过拟合。

你只有一个 24GB 消费级显卡和 3000 条人工标注的"好/差回答对"，想给 7B 模型做对齐。最现实的选择是？

一句话取舍：要极致效果且有算力团队 → PPO；要快速稳定落地 → DPO 家族。2024 年以来的行业现实是：绝大多数开源微调的对齐步骤，都停在 DPO。

上线与部署：导出、推理加速与数据回流闭环

训练完只是上半场。上线 = 把权重导出成推理引擎认的格式（merge），用 vLLM/llama.cpp 等引擎跑起来（必要时量化），再把线上 badcase 回流成下一轮训练数据——微调上线 → 收集 badcase → 数据回流再训练，闭环转起来模型才持续变好。

上线三步

步骤做什么常用选择
① Merge / 导出把 LoRA 等小模块的增量权重合回基座，或直接导出全量权重为通用格式merge 成 safetensors / GGUF；注意导出前先做最终评估
② 推理引擎加载权重、服务请求。关键是吞吐（每秒多少 token）和延迟（首字多快）GPU 服务器：vLLM（PagedAttention，高吞吐）；本地/边缘：llama.cpp（CPU 可跑）
③ 量化推理把权重精度降低换显存/速度，如 INT8、4bitAWQ / GPTQ（GPU）、Q4_K_M 等（GGUF）；注意：量化有轻微质量损失，对齐后的模型对量化更敏感，要复评
最常见的上线事故：训练评估全过，量化部署后用户投诉"变傻了"。对齐后的模型（尤其 DPO 后）行为分布更尖锐，量化误伤更明显。务必在"最终部署形态"（量化后、引擎里）再跑一遍评估。

badcase 回流闭环

数据回流闭环（点"下一步"逐步看）
上线服务：模型部署到真实流量，记录所有请求、回答、用户反馈（点赞/点踩/人工接管）。
badcase 挖掘：从日志里筛出问题样本——错误回答、被点踩的、触发安全拦截的、用户重复追问的（没答好的信号）。聚类归因：是知识问题、格式问题还是对齐问题？
构造修复数据：badcase 改写进训练集：知识错 → 补 RAG 或加事实数据；格式/偏好问题 → 改造成 DPO 偏好对（修好的是 chosen，线上的是 rejected）。
增量训练 + 回归评估：小步再训练（防止灾难性遗忘，参考第 1 课），必须跑回归集：确认新数据修了 bug，又没弄坏旧能力。
灰度发布：新版本先给 5% 流量，对比线上指标（点踩率、接管率、延迟），稳定后全量。闭环回到第一步。
判断一个团队微调是否成熟，不看它训出过什么模型，看它的回流闭环转了几圈。只训不回流，模型上线第一天就是它最好的一天。

线上用户大量点踩"回答太啰嗦"的样本，回流时最高效的用法是？

上线口诀：导出要 merge，推理选引擎，量化必复评，badcase 要回流。部署不是终点，是模型生命周期里"数据最多"的起点。
