鸭子的脊髓反射：大脑可以慢，反射必须快

摸到烫的东西，你先缩手、后喊疼——缩手根本不经过大脑。机器鸭同理：让关节站稳的「反射」必须在一块小芯片上毫秒级完成，而「思考去哪」可以交给慢半拍的大脑。

上一课我们认识了鸭子的「感官」：IMU 报告身体姿态，摄像头观察世界。但传感器只是收集信息，真正的问题是：谁来、在哪里、多快地把这些信息变成关节动作？答案分两层。

一层是「大脑」——上位机与大模型，负责看懂画面、理解指令、规划路线，一次思考要几十到几百毫秒。很慢，但没关系：「接下来往哪走」晚半秒决定也不致命。另一层是「反射」——身体正在倾倒，脚踝必须在几毫秒内调整力度；等大脑反应过来，鸭子已经脸着地了。

想象你的手碰到滚烫的锅：指尖的神经把信号传到脊髓，脊髓直接下令「缩手」，全程几十毫秒；等「烫」的感觉慢慢传到大脑皮层，你的手早就离开锅了——先行动、后觉得疼，这是脊髓反射弧的分工。机器鸭完全一样：IMU → 主控芯片 → 舵机这条「反射弧」必须毫秒级完成；而摄像头 → 大模型那条「思考回路」慢几百毫秒也能容忍。
大脑可以慢，反射必须快。本课的主角固件（firmware），就是住在那块小芯片里的「脊髓」——它不是跑完整操作系统的大程序，而是一段直接控制硬件、精简到极致的底层代码。

你摸到烫东西时，「缩手」这个动作是由身体的哪一部分直接完成决策的？

记住一句就够：固件不负责「聪明」，只负责「快而稳」。聪明的部分（视觉、大模型）交给大脑，固件守住毫秒级一拍的反射底线。

固件是什么：从按下电源到进入主循环

固件是烧写进主控芯片的底层程序。按下电源后的零点几秒内，它要完成一套「起床流程」，然后跳进一个永不退出的主循环，并把 1ms 心跳的定时器中断打开。

固件（firmware）＝固化在芯片里的软件。你手机上的 App 可以随时卸载重装，固件则写进芯片的存储器里、上电即运行——它是硬件与上层软件之间的第一座桥。对机器鸭来说，固件决定了「舵机多久更新一次、IMU 数据怎么读、摔倒了怎么办」这些生死攸关的事。

那么按下电源开关的那一刻，芯片里发生了什么？它不会立刻开始走路，而是先按部就班做完一套固定的「起床流程」。

就像你每天早上：睁眼（上电复位）→ 拉开窗帘知道现在是白天（时钟配置）→ 洗漱收拾（外设初始化）→ 检查钥匙钱包（自检）→ 出门开始一天的工作（进入主循环）。跳过任何一步都可能出乱子——没检查钥匙就出门，一天都白干。
分步点亮：上电之后芯片里的五步起床流程（教学示意，不同芯片略有差异）
① 上电复位 —— 电源芯片把电压稳定到额定值，复位引脚释放，芯片从一个固定地址开始执行第一行代码。
② 时钟配置 —— 芯片出厂时用内部慢时钟「苟着」，启动后切换到外部高速晶振，把主频拉满。
③ 外设初始化 —— 逐一配置定时器、串口、IMU 接口与舵机总线，给它们排好班、定好职责。
④ 自检 —— 读一次 IMU 确认有数据、扫描总线确认 15 个舵机都在线、检查电池电压；发现问题就进入安全模式（比如趴下并亮灯，教学示意），绝不带着故障硬跑。
⑤ 进入主循环 —— 启动 1ms 定时器中断，跳进 while 主循环，从此永不退出——直到断电，或被看门狗重启（第 7 章详谈）。
主循环负责「慢事务」，定时器中断负责「快事务」——这个分工从上电那一刻就定下了。中断循环怎么跑，第 5 章拆开细讲。

固件上电自检（确认 IMU 可读、舵机在线、电量正常）最主要的意义是什么？

固件 = 上电后自动运行的「起床流程 + 永不退出的主循环」。它的第一要务不是聪明，而是让所有硬件进入可预测、随时待命的状态。

实时性与 1kHz：为什么是 1ms 一拍

「实时」的真含义不是「快」，而是「按时」。关节控制通常跑在几百到上千赫兹的量级——本课按教学常用值 1kHz（每 1ms 一拍）来讲（教学估算，Microduck 真实控制频率以厂商固件为准）。

第 01 课的演示你已经见过：控制频率太低，鸭子被推一下就越晃越大。这类小型双足机器人的关节稳定回路，业界通常放在几百到上千赫兹——本课统一按 1kHz 教学，即每 1 毫秒一拍。

为什么执着于「毫秒」？因为身体开始倾倒之后，留给抢救的时间只有几百毫秒量级；要把一次倾倒拆成十几二十次「感知—修正」的小步完成，每一步就必须在几毫秒内做完。拍子慢了，鸭子依据的就是「过期」的身体状态，修正全踩在错误的节拍上。

这里一口气引入四个术语，之后每一章都会反复用到——引入即解释：

点击卡片翻面，收下实时系统的四张「黑话卡」
实时 real-time
指系统「保证在时限内完成」，跟「快」不完全是一回事——跑得慢但永远按时交卷，也算实时。
截止期 deadline
这一拍工作必须完成的最后期限。1kHz 系统里，截止期就是「本拍开始后 1ms 之内」。
硬实时 hard real-time
错过截止期即失败。关节控制就是硬实时：修正迟到一步，物理世界里就是一次真摔。
抖动 jitter
同一件事每次发生的时刻并不完美等间隔，这个波动幅度叫抖动。第 5 章的核心演示会把它画出来。

在线看视频软实时画面卡一下——烦人，但不丢人

「看视频卡顿」与「关节控制卡顿」的本质区别是什么？

判断一个系统是不是硬实时，只问一个问题：错过一次截止期的后果，是「体验变差」还是「物理世界出事」？鸭子给出的答案是后者。

固件分层架构：一家三层小公司

应用层定「去哪」，运动层翻译成「每个关节转多少度」，驱动层负责「总线上真的发出去、传感器真的读回来」——像公司三层级，各司其职，出了问题才知道该找谁。

把固件所有代码糊成一团，初期跑得快，后期改一行崩全身。工程上的解法是分层。机器鸭的固件（教学简化模型）大致分三层：

层类比职责一句台词
应用层老板决定「做什么」：步态策略、模式切换、与上位机通信「下一步落脚在右前方 5 厘米」
运动层中层管理者把意图翻译成关节语言：运动学映射、姿态融合、平衡修正「右髋转到 32 度、右膝弯 15 度……」
驱动层一线员工与硬件直接打交道：总线收发、IMU 读取、定时器配置「收到，这就把目标角写上总线」
公司里，老板不需要知道快递员今天开什么车，员工也不用过问公司战略——大家只需要一份清晰的岗位职责表。分层的好处一模一样：想把总线方案换掉？只改驱动层；想换一种步态？只动应用层。每层的替换都不波及邻居，这就是好架构。
把一条「迈步指令」在三层之间的流动排成正确顺序
驱动层：把目标角度按协议打包，写进舵机总线
应用层：步态策略给出「右脚向前迈 5 厘米」
应用层：根据上报的新状态，决定下一步怎么走
驱动层：读回 IMU 与舵机状态，向上层上报
运动层：把落脚点映射成 15 个关节的目标角度

应用层说了一句「右脚向前迈 5 厘米」，这件事最终由谁变成 15 个关节的具体角度？

分层的检验标准：任何一层的替换都不应波及其他两层。做复刻项目时，先把三层的接口定义清楚，再动手写代码，能少走很多弯路。

1kHz 定时器中断循环：固件的心跳

定时器每 1ms 强行「打断」主程序一次：读 IMU、算关节、发指令、喂狗、记耗时——这一套必须赶在下一次打断前干完。干不完就是超时，下面的演示会把它标红给你看。

中断（interrupt）是什么？主循环正在慢悠悠做事时，定时器像闹钟一样每 1ms 响一次，CPU 无论在干嘛都立刻放下手头工作、跳去执行中断服务程序——做完马上回来接着干。1kHz 的控制频率对应的周期是：

$$f = 1000\ \text{Hz} \quad\Rightarrow\quad T = \frac{1}{f} = 1\ \text{ms}$$

中断服务程序里，每一拍干五件事，逐项拆解：

① 读 IMU——感知：此刻身体什么姿态，第 05 课的传感器在这里派上用场。② 算目标角——决策：上层策略的输出加上平衡修正，得出 15 个关节这一拍该到的角度。③ 发总线——执行：把目标角写出去（时间预算多紧张，第 6 章细算）。④ 喂看门狗——报平安「我还活着」（第 7 章详谈）。⑤ 记耗时——给每拍打上时间戳，超时就计数报警，调试时这就是「病历本」。

// ===== 主循环：慢路径，做不赶时间的事 =====
while (true) {
    处理上位机发来的新指令        // 往哪走、做什么动作
    刷新指示灯与状态日志          // 不赶时间
}

// ===== 定时器中断：每 1ms 强行打断一次（教学示意） =====
on_timer_interrupt_every_1ms:
    读取 IMU 姿态                  // 感知：身体现在什么状态
    计算 15 个关节的目标角度        // 决策：策略输出 加 平衡修正
    通过舵机总线下发目标角度        // 执行：时间预算见第 6 章
    喂看门狗                       // 报平安：我还活着
    记录本拍耗时，超时则计数报警    // 给调试留下证据

关键约束来了：这五件事的总耗时必须明显小于 1ms，还要给「万一哪拍慢一点」留出余量——这正是第 3 章说的截止期落到实处。下面的演示让你亲手把「单拍计算耗时」拉过预算线，看看超时是怎么发生的：

控制拍时间轴：耗时、周期与抖动的三角关系

仔细观察：把抖动幅度调大后，即使平均耗时没超预算，个别「倒霉拍」也会冲破截止期标红——这就是抖动与超时的关系。所以工程上通常要求平均耗时只占预算的一半左右：余量就是留给抖动的（经验法则，教学估算）。

如果某一拍的计算耗时超过了中断周期，最直接的后果是什么？

一句话：中断循环是固件的心跳，心跳的纪律是「每拍必到、每拍按时」。本课剩下的内容——总线预算、状态机、看门狗——全都在为这一句服务。

半双工 UART 舵机总线：一条线上的轮流传话

15 个舵机共用一条数据线，像一条对讲机频道：主控喊话报 ID，被点名的应答，其余闭嘴。半双工省了线，代价是同一时刻只能一人说话——于是每拍的时间预算必须精打细算。

15 个关节舵机如果每个都单独拉一组线回主控，接插件会多到可怕，装配也是噩梦。常见做法是总线式：所有舵机并挂在同一对线上，半双工 UART 是这类小型机器人常用的方案之一（Microduck 的具体总线形式以厂商资料为准）。

半双工（half-duplex）＝收发共用同一条线，任一时刻只能一个方向说话。好处是省线、省引脚；代价是主控与舵机必须轮流「抢话筒」——这就引出了协议帧和时间预算两件事。

字段大小（教学示意）作用
帧头2 字节唤醒总线上所有设备：「注意，有话要说」
舵机 ID1 字节点名：只有 ID 匹配的舵机继续接收，其余忽略
指令1 字节干什么：写角度、读状态……
参数若干字节具体数据：目标角度、速度限制等
校验和1 字节接收方核对，算错就整帧丢弃（帧结构为教学示意，以厂商手册为准）
分步揭示：一帧指令是怎么发出去的（教学示意）
① 抢话筒 —— 半双工线上同一时刻只能一方说话，主控先把总线方向切到「发送」。
② 喊帧头 —— 发出连续两个帧头字节，总线上所有舵机竖起耳朵：有话要说。
③ 报 ID 点名 —— 接下来的 ID 字节，只有与之匹配的那只舵机继续听，其余 14 只全部忽略。
④ 指令与参数 —— 「转到目标角度、以这个速度」——具体数据写在这一段。
⑤ 校验与回话 —— 接收方核对校验和，错了整帧丢弃；需要回包时总线方向翻转，轮到舵机说，主控闭嘴听。

接下来算一笔硬账：波特率 115200 时（教学估算），每个字节在线上要占 10 个位——8 个数据位加上起始位与停止位：

$$t_b = \frac{10}{115200}\ \text{ms} \approx 0.0868\ \text{ms}$$

一帧指令加一帧应答共约 16 字节，一来一回约 1.4 毫秒——一问一答就吃掉了一整拍的预算。15 个舵机全轮询一遍要 20 毫秒以上，显然不可能每拍都做。出路无非三条：提高波特率、精简帧长、或者把「写」与「读」拆成不同频率——写目标角每拍必须发，读状态可以隔几拍轮询一只。下面的演示把这笔账算给你看：

你会看到：波特率一低、舵机一多，彩色段立刻越过红色预算线。真实固件通常不会每拍轮询全部 15 只——「写」走广播或只写关键关节，「读」分摊到不同拍，才能既保住 1kHz 又拿到足够新的状态（教学示意，具体策略以厂商固件为准）。

半双工总线上，如果主控和一只舵机同时开口说话，会发生什么？

一个常见误区：以为波特率越高越好，无脑拉满——线一长、舵机一多，高速信号容易出错包，校验失败后重传反而更慢。波特率要与线材长度、舵机数量、电路板布局一起权衡（教学经验，以厂商固件为准）。
总线设计的本质是算账：波特率 × 帧长 × 舵机数 ＝ 每拍总线时间，必须留足余量。会算这笔账，你就比大多数入门者更懂固件。

状态机与看门狗：摔倒了就自己爬起来

固件用状态机管理「现在是站着、走着、摔倒恢复还是充电」，异常来临时按预演好的剧本切换；看门狗则盯着程序心跳，卡死就断电重启——宁可短暂失联，不要永远趴窝。

状态机（state machine）：任意时刻系统只处于一个明确的状态，事件（收到指令、传感器判定、定时器到期）触发状态之间的切换。对双足机器人，最典型的四个状态是站立 / 行走 / 恢复 / 充电。

为什么需要状态机？因为同一套控制参数不能通吃所有场景——走路的参数拿去站立会抖，站立的参数起不了身。摔倒是双足机器人不可避免的事，所以「恢复」绝不靠临场发挥，而是预存好的一套起立剧本：检测到摔倒 → 切入恢复态 → 关节按剧本逐个回到指定角度 → 回到站立。

点击翻面：四种模式各自在忙什么
站立
静态保持平衡，舵机维持锁定力矩，等待上层指令。
行走

恢复
摔倒后的起立状态机：按预存序列逐关节执行，直到重新站直。
充电
趴下休眠，关闭运动输出，只保留电源管理与充电监测。

按预存的起立序列逐关节执行动作
IMU 姿态持续越界，固件判定：摔倒了

看门狗（watchdog）是芯片里一个自动倒数的计数器：固件必须每隔一小段时间把它清零，俗称「喂狗」；一旦程序卡死、忘了喂，计数器数到底就自动复位整块芯片——固件从第 2 章的「起床流程」重新跑一遍。它防的不是摔倒，而是「程序傻了」。

// ===== 顶层状态机（教学示意） =====
switch (当前模式) {
    case 站立:  收到行走指令，切换到 行走
    case 行走:  IMU 判定摔倒，切换到 恢复
    case 恢复:  按起立序列逐关节执行，完成后回到 站立
    case 充电:  关闭运动输出，只响应电源管理
}

// ===== 看门狗：只认「按时报平安」 =====
on_timer_interrupt_every_1ms:
    执行一拍控制
    重置看门狗计数器        // 这就是「喂狗」
// 一旦程序卡死、喂狗停止，计数器溢出，芯片自动复位重启

在 1ms 中断里做浮点重计算或大段循环——中断拖得越久，下一拍被推得越晚；重活应留给主循环或交给硬件外设（教学示意）。

在中断里死等总线回包——总线一慢，所有拍跟着超时；总线的收发都应做成非阻塞的。

状态迁移不设防——「恢复」执行到一半又收到行走指令就直接切过去，关节可能被硬掰；迁移条件要明确、互斥。

喂狗位置放错——只在和主循环无关的地方喂狗，主循环卡死了狗还活着；常见做法是主循环设置「我活着」的标志，中断确认标志后再喂（教学示意）。

看门狗在什么情况下会让整块芯片复位重启？

状态机管「出事了怎么办」，看门狗管「程序傻了怎么办」。一个负责优雅，一个负责粗暴——两手都要硬，鸭子才能长期活着。
